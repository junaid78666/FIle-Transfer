Weierstrass Equation & ECDH

The security of NIST P-256 relies on the Elliptic Curve Discrete Logarithm Problem (ECDLP). Given base generator point \( G \) and public key \( Q = d \cdot G \), computing private key \( d \) is computationally infeasible.

Point P (Alice): Sender's Ephemeral public point on curve
Point Q (Bob): Recipient's static NIST P-256 public key
Point R = P + Q: Intersecting chord and reflection yielding shared secret

End-to-End Pipeline

Zero-Trust Cryptographic Workflow

How files are secured, encapsulated, and decrypted without exposing plaintext to servers

01 Ephemeral Keypair

1. NIST P-256 Agreement

When Alice transfers a file, a cryptographically secure ephemeral keypair is generated in memory. Alice computes the ECDH shared secret using Bob's verified public key.

02 Key Derivation

2. HKDF-SHA256 Extraction

The raw elliptic curve shared coordinate is fed into HMAC-based Extract-and-Expand Key Derivation Function (HKDF) to derive an uncompromising 256-bit symmetric session key.

03 Payload Encryption

3. AES-256-GCM Vault

The original binary stream is encrypted using AES-256 in Galois/Counter Mode with a 96-bit unique IV. This ensures both confidentiality and 128-bit Galois authentication.

04 Integrity Verification

4. SHA-256 Audit Seal

Bob decrypts the session key using his password-unlocked private key. The decrypted payload is hashed with SHA-256 and matched against the sender's seal to guarantee zero tampering.

Project Defense FAQ

Technical Architecture Questions

Common questions regarding security implementation and academic evaluation

Why does the system use Hybrid Cryptography instead of pure ECC?
Elliptic Curve Cryptography is designed for asymmetric key agreement (ECDH) and digital signatures (ECDSA). Because asymmetric operations are mathematically intensive for multi-megabyte payloads, modern secure systems use ECIES (Elliptic Curve Integrated Encryption Scheme): ECC safely encapsulates a 256-bit symmetric session key, and AES-256-GCM encrypts the bulk file at hardware speeds.
How are receiver private keys protected on the server?
Private keys are never stored in plaintext. During registration, the user's password undergoes PBKDF2-HMAC-SHA256 with 100,000 iterations and a cryptographically random salt to derive a key-encryption key (KEK). The SECP256R1 private key is encrypted with AES-256-GCM using this KEK before database persistence. Even with direct database access, an adversary cannot decrypt transfers without the user's password.
How does the system detect tampering with encrypted files?
The system employs two independent layers of integrity protection: first, AES-256-GCM produces a 128-bit authentication tag that fails immediately if any ciphertext bit or nonce is altered. Second, a 256-bit SHA-256 cryptographic digest of the original file is recorded in the transfer record and re-verified byte-for-byte upon client decryption.
